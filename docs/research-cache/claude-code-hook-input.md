## 1. Does PostToolUse fire for AskUserQuestion, can a matcher select it, caveats?
- Matcher: yes. PostToolUse "Matches on tool name, same values as PreToolUse"; the PreToolUse list reads: "built-in tools such as `Bash`, `PowerShell`, `Edit`, `Write`, `Read`, `Glob`, `Grep`, `Agent`, `Workflow`, `WebFetch`, `WebSearch`, `AskUserQuestion`, and `ExitPlanMode`". So matcher `AskUserQuestion` is a documented tool name.
- PostToolUse "Runs immediately after a tool completes successfully." No page sentence says "PostToolUse fires for AskUserQuestion" explicitly; the only PostToolUse + AskUserQuestion text is the `updatedToolOutput` row: "In a Cowork cloud session, Claude Code ignores this field when the tool is `AskUserQuestion` or `ExitPlanMode`, and Claude reads the original answer or plan" (which implies the hook runs on it).
- Caveats documented: AskUserQuestion is a "requires user interaction" tool: in PreToolUse, `allow` alone is not enough, it needs `updatedInput` (with `answers`). PermissionRequest hooks also receive it, and `updatedInput` is required there too. `defer` (non-interactive `-p` only) names AskUserQuestion as the typical case. A third-party issue snippet (not opened, unofficial) says a PreToolUse hook can make AskUserQuestion return empty answers while PostToolUse works; unverified.

## 2. Shape of tool_input / tool_response for AskUserQuestion in PostToolUse
- `tool_input` (hooks.md, PreToolUse tool-input table, verbatim): `questions` array "each with a `question` string, short `header`, `options` array, and optional `multiSelect` flag", example `[{"question": "Which framework?", "header": "Framework", "options": [{"label": "React", "description": "Component library"}, ...], "multiSelect": false}]`; `answers` object, example `{"Which framework?": "React"}`: "Optional. Maps question text to the selected option label. Multi-select answers join labels with commas. Claude doesn't set this field; supply it via `updatedInput` to answer programmatically".
- Agent SDK user-input doc (the shape a `canUseTool`/`updatedInput` caller RETURNS, input side): `answers` keys are the `question` text, values the option `label`; multi-select "pass an array of labels or join them with `", "`"; free text / "Other": "put the user's text in `answers[question]`" ("not the word Other"); optional `response` freeform string ("Claude receives 'The user responded: ...'"). Options may carry `preview` (TS SDK only, opt-in).
- `tool_response` for PostToolUse: hooks.md says only "The exact schema for both depends on the tool." The AskUserQuestion `tool_response` shape is NOT documented anywhere read. Whether the TUI-answered answers appear in `tool_input.answers`, in `tool_response`, or both is not documented: measure in a spike. Do not infer it from the SDK `updatedInput` shape.

## 3. Subagent identification, absence on main thread, can a subagent call AskUserQuestion?
- hooks.md common-input text (verbatim): "`agent_id` and `agent_type` tell your script which agent a hook fired in, such as a subagent, an in-process teammate, or the agent you chose with `--agent`". `agent_id`: "Unique identifier for the subagent or in-process teammate the hook fires in." `agent_type`: "Agent name (for example, "Explore" or "security-reviewer"). Present when the session uses `--agent` or the hook fires inside a subagent. For subagents, the subagent's type takes precedence over the session's `--agent` value."
- Consequences: `agent_type` is also present on the MAIN thread when the session was started with `--agent`, so its presence alone does not mean subagent; `agent_id` is documented as the subagent/teammate identifier. "Absent on main-thread calls" is implied for `agent_id` but never stated verbatim (the TaskCreated/TaskCompleted rows say "May be absent"). Other fields seen in the common table: `prompt_id`, `scratchpad_dir`, `effort`.
- Subagent AskUserQuestion: Agent SDK doc, Limitations: "`AskUserQuestion` is not currently available in subagents spawned via the Agent tool". hooks.md says nothing on it. (SDK doc, not the interactive CLI doc; CLI behaviour unverified.)

## 4. Common input fields; is cwd the project root?
- Table (verbatim): `session_id` "Current session identifier"; `transcript_path` "Path to conversation JSON. The transcript file is written asynchronously and may lag the in-memory conversation..."; `cwd` "Current working directory when the hook is invoked"; `permission_mode` one of `"default"`, `"plan"`, `"acceptEdits"`, `"auto"`, `"dontAsk"`, `"bypassPermissions"`; `hook_event_name` "Name of the event that fired". Also `prompt_id`, `scratchpad_dir`, `effort`.
- No guarantee of project root. Verbatim: "`cwd` follows Claude: the `cwd` field in the hook's input JSON is the worktree root after Claude enters a worktree, and the new directory after Claude runs `cd`." If the directory no longer exists, command hooks run from a fallback directory with a logged warning. The project root is exposed through `$CLAUDE_PROJECT_DIR` (from model knowledge, not re-read this run).

## 5. Can PostToolUse modify or block for AskUserQuestion? Ordering?
- PostToolUse decision fields (verbatim): `decision: "block"` "adds the `reason` next to the tool result. Claude still sees the original output; to replace it, use `updatedToolOutput`"; `additionalContext` "String added to Claude's context alongside the tool result"; `updatedToolOutput` "Replaces the tool's output with the provided value before it is sent to Claude. The value must match the tool's output shape" (ignored for AskUserQuestion/ExitPlanMode in a Cowork cloud session); `updatedMCPToolOutput` MCP only.
- It cannot undo the call: exit 2 on PostToolUse "Shows stderr to Claude; the tool already ran." "`updatedToolOutput` only changes what Claude sees. The tool has already run by the time the hook fires, so any files written, commands executed, or network requests sent have already taken effect." So not a gate, but it can add context or rewrite what Claude sees.
- Ordering: a synchronous (non-`async`) hook finishes before Claude Code records the tool result: "Synchronous responses only: Claude Code ignores the field in the response of a hook that runs in the background, because that response arrives after Claude Code records the tool result." `async: true` "runs in the background without blocking" and "can't block or rewrite the result". Matching hooks of one event run in parallel. Not stated in one sentence: "a sync PostToolUse hook's file write precedes the model's next tool call"; it follows from the above (sync hooks complete before the result is recorded and sent) but is inference, not a quote. A PostToolBatch event exists "after a full batch of parallel tool calls resolves, before the next model call".

## 7. SubagentStop (read 2026-11-20, hooks.md "### SubagentStop", Claude Code docs as of this date)
**Input fields.** Common fields plus (verbatim): "SubagentStop hooks receive `stop_hook_active`, `agent_id`, `agent_type`, `agent_transcript_path`, and `last_assistant_message`. The `agent_type` field is the value used for matcher filtering. The `transcript_path` is the main session's transcript, while `agent_transcript_path` is the subagent's own transcript stored in a nested `subagents/` folder. The `last_assistant_message` field contains the text content of the subagent's final response, so hooks can access it without parsing the transcript file." Also `background_tasks` and `session_crons` arrays (scoped to the parent session). Documented example:
`{"session_id":"abc123","transcript_path":"~/.claude/projects/.../abc123.jsonl","cwd":"/Users/...","permission_mode":"default","hook_event_name":"SubagentStop","stop_hook_active":false,"agent_id":"def456","agent_type":"Explore","agent_transcript_path":"~/.claude/projects/.../abc123/subagents/agent-def456.jsonl","last_assistant_message":"Analysis complete. Found 3 potential issues...","background_tasks":[],"session_crons":[]}`
- `stop_hook_active` (Stop doc): "`true` when Claude Code is already continuing as a result of a stop hook". Loop protection: 8-consecutive-continuation cap (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` raises it), counter resets when Claude calls a tool.
- Final text = `last_assistant_message`. CAVEAT, Claude Code v2.1.271+: a subagent running with the `SubagentHandback` tool delivers its report through that tool before stopping; then `last_assistant_message` "holds the subagent's closing text, if any, which is not the delivered report. The report is that call's `message` input, which a `PreToolUse` or `PostToolUse` hook matched on `SubagentHandback` receives as `tool_input.message`." Which agents run with `SubagentHandback` was not read (the tools-reference page was not opened): check before relying on `last_assistant_message`; fallback is `agent_transcript_path` (file may lag: the main-transcript async-write warning is documented, its application to subagent transcripts is not stated).
- Internal agents: SubagentStop also fires for Claude Code's own internal agents (prompt suggestions, `/btw` side questions). For those `agent_type` is the session's `--agent`/`agent` setting name, or an empty string. A matcher naming agent types does not match an empty `agent_type`; an omitted/`""`/`"*"` matcher does.

**Matcher.** Yes, filters on agent type: "Matches on agent type, same values as SubagentStart": `general-purpose`, `Explore`, `Plan`, custom agent names, plugin-scoped names like `^my-plugin:reviewer$`. sub-agents.md: matcher value is the agent's frontmatter `name` (project/user subagents), or the plugin-scoped identifier `my-plugin:db-agent`; a scoped name contains a colon so it is evaluated as an unanchored regex, anchor with `^...$`. `name` frontmatter: "Hooks receive this value as `agent_type`." Names cannot contain `:`.

**Blocking and exit codes.** Yes. "SubagentStop hooks use the same decision control format as Stop hooks": `decision: "block"` + `reason` "keeps the subagent running and delivers `reason` to the subagent as its next instruction"; exit 2 "delivers its stderr message the same way" (exit-code table: SubagentStop, can block: "Prevents the subagent from stopping"). `hookSpecificOutput.additionalContext` (with `hookEventName: "SubagentStop"`) is non-error feedback that also keeps it running. JSON `continue: false` takes precedence over exit 2 and ends the subagent. Exit 2 with empty stdout and stderr saying a file is missing (`No such file or directory`) is treated as a NON-blocking error (a missing script does not trap the subagent). Other exit codes: standard (non-2 is a non-blocking error; not re-read for this event). A prompt/agent-type hook `ok:false` on SubagentStop feeds the reason back unless `impossible: true`.
- Recording-only hook: exit 0 with no `decision` leaves the stop unaffected.
- Sync ordering vs the parent's Agent tool result: NOT documented for SubagentStop. The only related text: "To inject context into the parent session after a subagent returns, use a `PostToolUse` hook on the `Agent` tool instead" (implies SubagentStop output does not reach the parent). Whether a sync SubagentStop command hook completes before the parent receives the Agent result (foreground) is not stated; for a background agent the parent gets a later completion notification. Measure in a spike (timestamp in the hook vs the next tool call) before relying on it; a PostToolUse hook on the Agent tool is the documented synchronous point (see below).

**Background and SendMessage-resumed agents.** NOT documented on the hooks or sub-agents page. Documented: settings-file hooks "`SubagentStart` and `SubagentStop` fire when a subagent starts or finishes"; sub-agents.md says by default subagents Claude spawns "already start in the background", and "When Claude sends a completed subagent a message with the `SendMessage` tool, the subagent resumes in the background without a new `Agent` invocation." Nothing says SubagentStop fires again on each resumed run. Issue-tracker snippets only (unopened, unofficial): one reports SubagentStop fires when a background subagent completes on its own, and another (claudeissues.com #92716) reports it does NOT fire when a background subagent is killed via TaskStop or "Exit and stop tasks"; SendMessage resume has several open bug reports. Treat "fires once per completion, including resumes" as unproven: spike it.

**PostToolUse on matcher `Agent` (alternative).** `Agent` is a documented matcher tool name (Q1 list). `tool_input` (Agent, PreToolUse table): `prompt` (string), `description` (string), `subagent_type` (string, e.g. "Explore"), `model` (optional alias). `run_in_background` is NOT listed in the Agent table (listed only for Bash/PowerShell), though the Agent tool exists with background behaviour. `tool_response` foreground, verbatim: "When a foreground Agent call completes, your PostToolUse hook receives the subagent's result and run telemetry in `tool_response`": `status` ("completed"), `agentId`, `content` (e.g. `[{"type":"text","text":"Found 12 endpoints..."}]`, the final text blocks), `resolvedModel`, `modelsUsed` (only if model swapped mid-run), `totalTokens`, `totalDurationMs`, `totalToolUseCount`, `usage`. Background launch: "returns immediately", `status: "async_launched"`, `agentId`, `description`, `prompt`, `outputFile`, `resolvedModel`, no result text and no usage: so PostToolUse(Agent) sees the verdict ONLY for foreground calls; a background agent's report arrives later as a completion notification (no documented hook for it besides SubagentStop). PostToolUse sync ordering: see section 5.

**Spoofing / who sets `agent_type`.** Not documented as a security property. What is documented: `agent_type` for a subagent is "the value used for matcher filtering" and comes from the agent's frontmatter `name` ("Hooks receive this value as `agent_type`"), with the subagent's type taking precedence over the session's `--agent`. The `subagent_type` in `tool_input` is the model's argument; that the harness derives hook `agent_type` from the resolved agent definition rather than echoing a raw tool argument is an inference, not a quote. Two real caveats from the docs: (a) an agent definition file's `name` is chosen by whoever can write `.claude/agents/` (or plugin/user dirs), so type is only as trustworthy as that directory is protected; (b) the main thread cannot set `agent_type` via tool input, but it can pick any existing `subagent_type`, and the model can name an arbitrary prompt: the identity proves "which definition ran", not "what it was told".
