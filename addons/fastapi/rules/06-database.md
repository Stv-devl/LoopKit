## Migration Rules

**Always use the migration command:**

```
/database:migration
```

It wraps Alembic: it reads the models, generates the revision, and makes you
read the generated file before it is applied.

**Commands:**

```bash
alembic revision --autogenerate -m "description"  # Generate from model changes
alembic upgrade head                              # Apply
alembic downgrade -1                              # Rollback one revision
alembic history                                   # List revisions
alembic current                                   # Where the DB actually is
```

**Forbidden:**

- Writing a revision file by hand in `alembic/versions/`
- Changing the DB directly with SQL outside a migration
- Applying an autogenerated migration without reading it

**Why the last one is not paranoia** — `--autogenerate` compares the models to
the *connected* database. It routinely gets these wrong:

- **Column rename** → emitted as `drop_column` + `add_column` = data loss.
  Rewrite it as `op.alter_column(..., new_column_name=...)`.
- **Type change** → often needs an explicit `postgresql_using` cast.
- **Server defaults, `CHECK`, partial indexes, extensions** → frequently missed
  entirely; add them by hand.
- **Anything created outside the models** (views, triggers, `pg_cron` jobs,
  extensions) → invisible to autogenerate, and sometimes *dropped* by it.
- **Empty revision** → means the models and the DB already agree, or that
  `target_metadata` does not import your models. Check `alembic/env.py` before
  concluding "no change needed".

## Naming

Alembic names files `<revision_hash>_description.py`. Keep the message short and
imperative: `-m "add lots table"`, `-m "index documents on tenant_id"`.

## Schema conventions

- Primary keys: UUID, never a bare autoincrement on a multi-tenant table. The
  patterns in `.claude/skills/` are written with **`uuid4_str`, i.e. `Mapped[str]`**
  — services take `tenant_id: str`, `get_current_user` returns a `User` whose
  `.id` is a `str`. Switching to native `uuid.UUID` columns is a legitimate
  choice; make it **once, here**, and change the patterns in the same pass. Half
  the codebase on each is a cast at every boundary.
- `TenantMixin` on every business entity — adds `tenant_id` FK **and its index**
- `TimestampMixin` — `created_at` + `updated_at`
- Composite index on `(tenant_id, <frequently filtered column>)`; a lone
  `tenant_id` index is not enough for a filtered list query
- Explicit `String(N)`, never a bare `String`
- FK with `ondelete=` set on purpose — cascade or restrict, decided, not default
- `Mapped[T]` for required, `Mapped[T | None]` for nullable

## Inspection commands

```bash
psql "$DATABASE_URL" -c "\dt"                      # Tables
psql "$DATABASE_URL" -c "\d+ <table>"              # Columns, indexes, FKs
psql "$DATABASE_URL" -c "select count(*) from <table>;"
alembic current                                    # Applied revision
```
